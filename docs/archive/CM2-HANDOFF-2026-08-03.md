## 0. THE SOLVE — why no custom firmware lit an LED

Found by disassembling stock v0.6.1 (six parallel analysts + adversarial verify),
then confirmed on-device by reading the live registers back over serial. Two
independent causes, both of which had to be fixed:

**Cause 1 — the LED power rail is gated by GPIO 36/37/38, and 36 was never driven.**
`wl_io::init_top_board_power_gpio` (`0x42008f38`) configures GPIO 36/37/38 as outputs
and sets `37=1, 36=0, 38=1` at boot. **GPIO 36 is the addressable-LED VDD enable
(active-high)** — stock only raises it inside its lights-enable path
(`0x4200aa78 → gpio_set_level(36,1)`, at `0x42008fc8`). Every prior custom attempt's
GPIO "enable sweep" **excluded 36 and 37**, assuming they were octal-PSRAM pins. So
the strips' supply was simply never turned on. (37 and 38 are additional top-board
rails; drive all three high.)

**Cause 2 — battery-backed pad holds latched from stock's last power-off.** Stock's
OFF recipe (`0x4201c788`) drives 36/37/38 LOW, then calls `gpio_hold_en(44)` +
`gpio_deep_sleep_hold_en()`. The latter sets `RTC_CNTL_DIG_ISO_REG` (`0x60008094`)
bit 11 (DG_PAD_AUTOHOLD_EN), which auto-holds **every digital pad** at deep-sleep
entry; holds live in the RTC domain (`0x60008094` / `RTC_CNTL_DIG_PAD_HOLD_REG`
`0x600080dc`) which is **battery-backed and survives a flash/reset**. So after any
stock power-off, `gpio_set_level` on a held pad is silently ignored — which also
explains why the old enable-pin sweep's control stage was dark. Stock's `app_main`
(`0x42019880`) releases these holds as its very first act; no custom firmware did.

**Cause 3 (build) — octal PSRAM claims GPIO 33-37.** On the N16R8, enabling octal
PSRAM maps GPIO 36/37 to SPIIO/DQS, making them undrivable. Build with
`CONFIG_SPIRAM=n` (stock runs PSRAM-off for exactly this reason).

**The driver was never the problem.** The vendored `led_strip` is byte-identical
upstream **espressif/led_strip v3.0.x** (config layout v3: `color_component_format`
= `0x600000E1` = GRB at struct offset +12). A v2.5.5 SPI build emits an identical
WS2812 waveform, so the version mismatch alone could not have darked the LEDs.

**The fix (in `fw-idf/src/main.c`), in order:**
1. Release holds — `gpio_deep_sleep_hold_dis()`, `gpio_hold_dis()` on 6/7/36/37/38/44,
   `rtc_gpio_hold_dis()` on 2/19/20, then force-unhold + zero `0x600080dc`.
2. Drive GPIO 36/37/38 HIGH (config as outputs, `36=1` is the enable).
3. `led_strip_new_spi_device` × 2: keys GPIO7/13/SPI2, underglow GPIO6/8/SPI3, GRB WS2812.
4. `led_strip_set_pixel` / `led_strip_refresh` per LED.

**On-device confirmation** (live `dump` after flashing): `GPIO_OUT1=0x70` (36/37/38
high), `DIG_PAD_HOLD=0`, `DIG_ISO` autohold-bit clear + force-unhold-bit set,
`GPIO_ENABLE=0xC0` (6/7 driving SPI data). All 21 LEDs individually addressable.

## 2. Recovery — proven, not theoretical

Stock firmware has been restored successfully **twice**, verified each time by
checking `sys.version` returned and `keymap.json` checksum unchanged.

```bash
cd ~/AI/worklouder
P=$(ls /dev/cu.usbmodem*) && ./.venv/bin/esptool --port $P write-flash 0x0 \
    firmware/firmware_v0.6.1_merged.bin
# ~13s. sha256 c0d288d5e709cbd7c3f5e4e11e57e26dd1e07e6d83c513e84a9f19d08039794b
```

Three independent recovery paths:
1. **`{"rescue":"rear_button_via_ulp"}`** — returned by `sys.bootloader`. Rear
   button + ULP watcher re-enters ROM bootloader *in hardware*.
2. **USB-Serial-JTAG** is fuse-enabled and cannot be disabled by a bad flash.
3. **`BOOT` + `RESET` buttons** physically on the control board.

Custom builds set `CONFIG_ESP_CONSOLE_USB_SERIAL_JTAG=y` so a serial port is
always present — esptool can reconnect without touching buttons.

### Entering the bootloader

`./enter_bootloader.sh` — calls `sys.bootloader` over the vendor RPC, waits for
`/dev/cu.usbmodem*`, prints the path. Needed before each esptool call **when stock
firmware is running**, because esptool's hard reset returns control to the app
(which uses USB-OTG/TinyUSB HID, so the JTAG port vanishes). Custom builds keep
the port permanently, so it's a no-op then.

## 4. Vendor RPC protocol — fully working

Recovered from **`@worklouder/wl-device-kit@0.1.29`**, which ships *unpacked with
source maps* inside `input.app`. 110 original TypeScript files extracted to
`wl-device-kit-src/` — `src/wl_device_comm/wl_device_comm_impl.ts` documents the
wire format in comments.

### Transport

Vendor HID collection: **usage page `0xFF00`, usage `0x01`, report ID 6**, 63-byte
Input + Output (BLE additionally exposes a Feature report; USB does not).

```
64-byte HID report (node-hid layout):
  [0] 0x06        report ID
  [1] channel     1 = debug log, 2 = RPC
  [2] length      payload bytes this packet (max 61)
  [3..] UTF-8 JSON payload, split across packets if longer
```

- Requests are raw JSON with **no trailing newline**.
- Responses are `\r\n` terminated and the terminator usually arrives in **its own
  follow-up packet** (`06 02 02 0d 0a`). Must accumulate per channel until a
  newline appears.
- 50 ms inter-request cooldown; call `id` must be in `[0, 999)`.
- **IOKit asymmetry (cost me an hour):** `IOHIDDeviceSetReport` takes the report ID
  as a separate argument and a buffer *without* it (63 bytes = `[channel, len,
  payload…]`), but the **input-report callback delivers the full report including
  the leading `0x06`**. So receive offsets are `channel=b[1]`, `len=b[2]`,
  `payload=b[3..]`.

### macOS access

- Must open with **`kIOHIDOptionsTypeNone`** (non-exclusive). The device presents a
  keyboard collection, and macOS refuses an exclusive seize.
- **cython-hidapi cannot do this** — it always seizes and exposes no toggle. Hence
  the Swift/IOKit tools.
- Terminal needs **Input Monitoring** (already granted). Symptom if missing:
  `IOHIDDeviceOpen` succeeds but `SetReport` returns `kIOReturnNotPermitted`
  (`0xE00002E2`).

### Lighting findings

`lights.preview` **works** and is the only functional colour path:

```json
{"backlight":{"effect":"solid","brightness":1,"speed":0.5,"magic":1,"color":16711680},
 "underglow":{"effect":"solid","brightness":1,"speed":0.5,"magic":1,"color":255}}
```

Effects implemented in firmware: `solid snake rainbow gradient shallow_breath off`.
(Note the vendor SDK enum says `breath`; the **firmware** says `shallow_breath` —
they disagree, which is itself evidence the surface is unstable.)

`v.oai.*` registration is **variant-gated**:

| method | result on this board |
|---|---|
| `v.oai.thstatus` | `{"ok":1}` registered |
| `v.oai.rgbcfg` | `{"ok":1}` registered |
| `v.oai.hid` | `404 Method not found` |
| `v.oai.rad` | `404 Method not found` |
| `nope.notreal` (control) | `404` — proves 404 means unregistered |

**`v.oai.rgbcfg` accepts and acks anything but ignores colour payloads.** It
returns `ok:1` even for `params:null`, so `ok:1` proves nothing. Tested and
visually confirmed no-ops: `{keys:{effect,color,...}}`, `{keys:{...},ambient:{...}}`
with full 5-field inner shape, a 13-element `keys` colour array, the same via
`lights.preview`, and after "arming" with
`{"syncKeysLighting":true,"syncAmbientLighting":true,"act":1}` (those three
camelCase identifiers appear in its handler's string pool alongside
`src/oai/wl_oai_bridge.cpp`). Conclusion: it is a control/ownership config method,
not a colour setter.

**There is no acquire/release primitive anywhere** in the SDK or firmware —
lighting is last-writer-wins. Firmware logs `OAI BRIDGE: init, v.oai.thstatus
registered on all variants`.

No per-key indicators exist anywhere in the 2.3 MB image: zero hits for
`per_key`, `perkey`, `rgb_matrix`, `set_key`, `key_color`, `led_index`, `colors`.
The firmware keeps per-pixel control internal.

## 5. LED hardware — extracted by disassembly (**the key result**)

The firmware links ESP-IDF's `led_strip` component, **SPI backend**:
`led_strip_new_spi_device`, `led_strip_set_pixel`, `led_strip_refresh`,
`led_strip_spi_*`. So these are single-wire WS2812/SK6812-family LEDs, **not** an
I2C matrix driver. (The I2C bus is the MAX77972 charger/fuel gauge:
`fuel_gauge_store`, `charger_controller`.)

**Init wrapper at `0x4200a980`.** Signature deduced from its stores:

```
entry a1, 64
memset(sp, 0, 20)                  ; 20 == sizeof(led_strip_config_t) in v2.5.5
...bitfield packing at sp+12...
4200a9c2:  s32i.n a2, a1, 0        ; strip_cfg.strip_gpio_num = arg a2
4200a9c4:  s32i.n a3, a1, 4        ; strip_cfg.max_leds       = arg a3
memset(sp+20, 0, 12)               ; 12 == sizeof(led_strip_spi_config_t)
4200a9d4:  movi.n a8, 4 ; s32i sp+20   ; spi_cfg.clk_src = 4
4200a9de:  s8i    -> sp+28             ; spi_cfg.flags.with_dma = 1
4200a9e1:  s32i.n a4, a1, 24      ; spi_cfg.spi_bus          = arg a4
4200a9ea:  call8 led_strip_new_spi_device(&strip_cfg, &spi_cfg, arg a5)
```

**Caller at `0x4200aa8c`** (the lights init; has an "already initialised" flag at
`obj+37`) makes exactly two calls:

```
4200aaa2:  addi   a13, a2, 28     ; &handle
4200aaa5:  movi.n a12, 1          ; spi_bus  = SPI2_HOST
4200aaa7:  movi.n a11, 13         ; max_leds = 13
4200aaa9:  movi   a10, 7          ; gpio     = 7
4200aaac:  call8  0x4200a980

4200aaaf:  addi   a13, a2, 32     ; &handle
4200aab2:  movi.n a12, 2          ; spi_bus  = SPI3_HOST
4200aab4:  movi.n a11, 8          ; max_leds = 8
4200aab6:  movi.n a10, 6          ; gpio     = 6
4200aab8:  call8  0x4200a980
```

So: **keys = GPIO 7, 13 LEDs, SPI2_HOST** and **ambient = GPIO 6, 8 LEDs,
SPI3_HOST**. 13 LEDs for 13 keys is one per key — **per-key RGB is physically
real.** Empirically corroborated: `lights.preview` with `backlight` red and
`underglow` blue produced "red keys + blue underglow", and one strip has exactly
13 LEDs.

Mapping rests on the Xtensa windowed-ABI assumption that for `call8` the caller's
`a10..a13` become the callee's `a2..a5`. **If the blocker turns out not to be
explained otherwise, re-verify this assumption first** — swapping gpio/max_leds
would give gpio 13 / 7 LEDs and gpio 8 / 6 LEDs, which fits the board worse but
isn't impossible.

Separately, `wl_io::init_leds_gpio()` configures **3 LEDC/PWM channels** for
single-colour *layer-indicator* LEDs (`set_layer_leds_brightness(u8,u8,u8)`).
Unrelated to the addressable strips. Pins not yet extracted.

## 6. What has been tried and FAILED — do not repeat

Custom firmware builds, flashes (hash-verified), boots, and its serial logs prove
every code path executes. **No LED has ever lit under custom firmware.**

| # | attempt | result |
|---|---|---|
| 1 | Arduino + `Adafruit_NeoPixel@1.12.3`, RMT, GPIO 7 (13) + GPIO 6 (8) | ran, logged all phases, **no light** |
| 2 | 26-pin GPIO "power enable" sweep, HIGH then LOW (1,2,3,4,5,8–18,21,38–42,45–48) | **nothing — including the control stage** |
| 3 | ESP-IDF `led_strip@2.5.5`, **SPI** backend, exact vendor config (SPI2/GPIO7/13, SPI3/GPIO6/8, WS2812, GRB, `with_dma=true`, default clk) | both strips init **without error**, **no light** |
| 4 | Matrix: SPI×WS2812, SPI×SK6812, RMT×WS2812, RMT×SK6812, plus enable-pin sweep of 43/44/46/0 | all init OK, **nothing** |

**Decisive control:** stock v0.6.1 lighting works perfectly *after* the teardown and
reassembly. So the `J2` ribbon is seated, the LED rail is powered by default, and
GPIO 7/6 are right. Attempt 2's dark control stage means there is almost certainly
**no power-enable GPIO to find**.

### Wrong assumptions made along the way (corrected — don't re-derive these)

- ❌ "LEDs are on an I2C matrix driver" → they are single-wire `led_strip`; I2C is
  the MAX77972 charger.
- ❌ "A switchable rail gates the LEDs" → over-read `PM recipe: ENTER STANDBY ->
  cut current to top-board domains`. That's a *standby* optimisation, not a boot
  gate. Cost two rounds of testing.
- ❌ "Maybe only ~7 LEDs exist, so per-key is impossible" → 13 + 8.
- ❌ "`v.oai.rgbcfg` returning `ok:1` means it worked" → it acks everything.
- ❌ rizin has an Xtensa disassembler → it does **not**. Use Espressif's
  `xtensa-esp-elf-objdump` (already installed, see §8).
- ❌ capstone 5.0.7 has Xtensa → it does not.

## 7. Recommended next steps, in order

### 7.1 JTAG the stock firmware (**strongly recommended first**)

`DIS_PAD_JTAG=False` and USB-Serial-JTAG is live, so OpenOCD can attach. Halt the
**working stock firmware** and read the truth instead of inferring it:

- Break at / after `0x4200aa8c` (lights init) or `0x4200a980` (strip wrapper).
- Read `a10`–`a13` at the call sites to **confirm gpio/max_leds/bus directly**.
- Dump `GPIO_OUT_REG`, `GPIO_ENABLE_REG`, the `IO_MUX` regs for GPIO 6 and 7, and
  the `GPIO_FUNCn_OUT_SEL_CFG` matrix entries — this reveals whether the signal is
  routed via IO MUX or GPIO matrix, and whether any *other* pin is driven that our
  firmware leaves alone.
- Dump the SPI2/SPI3 peripheral config for clock divider and mode.

Everything needed is installed except OpenOCD (`brew install open-ocd`, or use
PlatformIO's bundled `tool-openocd-esp32`). Target config: `esp32s3-builtin.cfg`.

### 7.2 Diff the register state

Flash a minimal app that, **at boot before touching anything**, dumps all IO_MUX +
GPIO matrix + SPI2/SPI3 registers over serial. Compare that against the JTAG dump
from stock. The delta is the answer.

### 7.3 Re-verify the ABI assumption

Independently confirm caller `a10→a2` for `call8` (see §5). Cheapest check: find
another call site in the binary whose argument values are unambiguous.

### 7.4 Identify `IC1`/`IC2`/`IC3`

Close-up photo of the three ICs beside `J2` on the control board. If they're
buffers/level shifters with an `OE`, that's the missing piece and it may be
controlled by a pin the sweep excluded or by something non-GPIO.

### 7.5 Lower-priority

- Mine the remaining pin map (matrix, encoder, joystick ADC, touch) — same
  technique as §5, anchors already located.
- The `fs`/`nvs` regions were never backed up (chunked dump kept failing at
  `0x100000` with `Serial data stream stopped`). `keymap.json` is readable via
  `fs.read`; a full `nvs` backup would need a working chunked read.

### Fallback that works today

If per-key stalls, `wllights` already gives whole-keyboard colour + effects over
USB **or** BLE, and `host.focused_app` + `linkedApps`/`linkedAppId` in the keymap
mean per-app *layer* colour is a supported vendor feature. A small macOS daemon
watching the frontmost app could drive `lights.preview` per app — real
functionality, just not per-key.
